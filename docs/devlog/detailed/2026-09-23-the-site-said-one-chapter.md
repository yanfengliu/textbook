# The site said one chapter, and CI could not finish, 2026-09-23

One worker on branch `site-and-ci`, off `main` at `f7cb330`, with main's `26d47cf` merged in on the way. Two defects from the project audit: the library page and `README.md` said only chapter 1 was ready with five published, and `ci.yml` could not pass as configured.

## The rule that reads the tree for which chapters can be read

`checkChapterAvailability` in `tools/check-content.js` has two halves. The contents half holds each book's `index.html` to its `chNN-` directories. The prose half reads the library page's shelf cards and `README.md` for sentences naming ready chapters, counts, and "N more are outlined". The texts now name no chapter, so the prose half passes them because they claim nothing, and it stays in place to fail a claim written back in. The run prints `0 statement(s) … compared` to say so. The proof is in `docs/learning/gate-proofs.md` and the defect in `docs/learning/defect-register.md`.

Things that went wrong while writing it, and a later change to it could trip over each:

- **Adjacent blocks ran together.** `textOf` joins text nodes with nothing between them, so a card's `<h2>The Living World</h2><p>Five of its 32…` read as "WorldFive". "Five" then had no word boundary, and the parser matched "32 chapters are written" instead. The real page has newlines between its elements and would have passed with the bug; a fixture written on one line caught it. `proseOf` now puts a space around each block element.
- **The first historical run failed the second book for its script.** At `6d854cf`, `tongjian/index.html` printed `可讀` and `未寫` under `lang="zh-Hans"`, and the rule, knowing only the Simplified words, failed it six times. The script has its own gate (`test/lexicon.test.js`), so the tag words are now accepted in both scripts, as `FIGURE_TOKENS` already does for 图 and 圖.
- **The failure message recommended a sentence the rule misread.** It told the author to "name exactly the chapters on disk". The independent review found that "Chapters 1, 2 and 3 are ready" was read as chapter 1 alone, so the sentence it asked for failed, and "Chapters 1 to 5 and 7" passed with 7 missing. Lists are now parsed as lists. The same review found that `&nbsp;` hid a claim and `&#8209;` cut "thirty-one" to "one", that `.soon` was claimed in the header and never checked, and that a card for a book with nothing on disk was skipped in silence. All four are fixed and tested, and so are most of its other eight findings; the proof entry says which were not. A focused second round on those fixes found that two of them had made new false positives. The list grammar read "Chapter 1, nine figures in all, is ready" as chapters 1 and 9, and a card with no link failed the true "Chapter 1 is in preparation". It also found that `&#1114112;` threw and stopped the whole check. A fix to a parser is itself a parser change, and it needs the same probing.
- **A sentence naming chapters is read as the whole list.** "Chapter 5, the newest, is ready" fails although it is true. That is on purpose, since all five defects in this class were partial lists; reword such a sentence rather than widen the parser.

## CI: three engines, 240 minutes, and a pinned image

`ci.yml` installed only chromium, and `tools/devices.js` launches WebKit and Firefox with no fallback. It now installs all three. The 30-minute limit could never be met, because unit, check, shot, flow and drive alone used about 15 minutes on the runner (910 s, run `35902188268`). The new limit is 240, with the estimate behind it written in the workflow. It was 180 until main's run `35940597512` and a second branch run showed the job reaching the end of drive at about 20.5 minutes, with drive 1.8 times its local time: scaled the same way, the whole job comes to about 72 minutes on this runner and about 145 on a 2-core one. The image is pinned to `ubuntu-24.04`, because the run's own annotation says `ubuntu-latest` moves to Ubuntu 26 from 2026-10-19, under the timings and the libraries `--with-deps` installs. A step now prints the runner's CPU count and memory, because the log did not say either.

- **The branch was run on GitHub before landing.** The brief said CI could not run from a branch, but `ci.yml` has a `workflow_dispatch` trigger, and `gh workflow run ci.yml --ref site-and-ci` runs the branch's own workflow. Run `35938466158` at `18b8ca1`: 4 logical CPUs and 15 GB; the three-engine install took 49 s and worked; unit, check (with the new rule, on Linux), theme, shot and flow passed. Then drive went red in 949 s on two `bilayer` steps, `curl-takes-the-wrap-away-and-the-sheet-rolls-up` (`3.1 -> 1.5 nm`) and `hot-enough-and-nothing-assembles` (`bilayer at t=8.05, 0.637 buried`). Both pass locally, and main's last two runs failed there too. `tools/test.js` stops at the first red step, so no run has reached `devices` or run long enough to test the timeout. That half is still unverified, and it stays so until the bilayer steps pass on Linux.
- **A YAML error was caught before it shipped.** The first version of the size step was `- run: echo "runner: $(nproc) …"`. That is a plain scalar holding `: `, which YAML reads as a mapping. Parsed locally, it failed with `mapping values are not allowed here`. On main it would have made the whole workflow invalid, so no run would have started at all and nothing would have been red to read. It is a block scalar now.
- **What else assumes the local machine.** `pinned` starts eight shards by default, and the runner has 4 CPUs. Its window counts animation frames, so its verdict holds on fewer cores. Its per-press timeouts, though, are 5 s of wall clock (`b.click({ timeout: 5_000 })` and the `focus` calls). A press that misses its timeout is skipped, not failed, so on an oversubscribed runner the tell is a lower press or key count in its totals, not a red step. The network is needed (Google Fonts and jsdelivr) and the runner has it. Nothing else found is specific to Windows or to this machine.
