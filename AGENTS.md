# AGENTS.md — textbook

## What this is

Web-based interactive textbooks. The first book is biology: chapters of set prose with hand-drawn SVG illustrations, animated diagrams, small simulations, and orbitable 3D models, read in a browser with no build step.

The book also tracks what a reader has learned and what they are struggling with, and reorganises practice around it: mastery per learning objective, a pure scheduler in the browser, and agent rounds that diagnose and write against what the record shows. `docs/design/textbook.md` is the design of record for the book, `docs/design/adaptive.md` for the study system, and `docs/work/` holds the rounds that produced both.

Non-goals: a content management system, accounts or progress sync, server-side rendering, and downloaded or generated raster art. Every illustration is authored SVG, canvas, or procedural 3D, so the repository holds no image pipeline.

Stack: plain HTML, CSS, and ES modules on Node 24 (`.nvmrc`); Three.js pinned through an import map for the 3D figures; Playwright chromium for the gates. Repo-only rules: `docs/policies/local-rules.md`.

## Fleet constitution

### Fleet Orchestration Policy

Deliver the requested outcome with verified correctness, coherent architecture, and minimal necessary complexity. Optimize for useful progress—not agent count, code volume, or maximum reasoning. Adapt rigor to risk. This policy grants no additional permissions or capabilities.

#### Roles

Only an explicitly designated agent acts as coordinator. Use one accountable integration owner per scope. The coordinator owns planning, dependencies, shared interfaces, architectural consistency, integration, and acceptance. It does not implement. Every change, however small, is delegated: the coordinator's session is where the next request arrives, and a coordinator in the middle of an edit cannot take it. Its own hands stay on what delegation needs — reading enough to write an assignment, and inspecting a handoff to accept or reject it.

Workers own bounded outcomes and local implementation decisions. They may use subagents within their scope and budget, but remain accountable. Organize threads around deliverables, not permanent departments. Avoid recursive manager hierarchies.

#### Plan and delegate

Inspect applicable instructions, relevant code/docs, working-tree state, and active tasks before changing anything. Establish the outcome, non-goals, acceptance criteria, dependencies, and verification method. Resolve routine ambiguity through evidence and reversible defaults.

Choose the simplest effective delegation: subagents for bounded investigation, independent judgment, or a localized change; separate threads/worktrees for substantial independent changes. Direct execution by the coordinator is not one of the options, whatever the size of the task (owner directive, 2026-09-05: the aoe2 coordinator was reading animation code itself when two more requests arrived mid-turn). Agree on shared contracts before parallel implementation. Avoid duplicate or blocked work. Size the team to the work continuously (owner directive, 2026-09-15, maps). Widen it when one worker holds the critical path and independent work is waiting. Narrow it when workers contend for the same file, port, or CPU. A worker does not run while another is editing the same file in the same tree, running the same gate, or holding a resource that cannot be shared. An expensive gate is such a resource: exactly one runs at a time, and the other workers are chosen around it (maps: `npm run visual` is a three-hour command that owns a port and the whole CPU).

Each assignment must identify its owner, outcome, relevant context, dependencies/contracts, base revision, workspace, allowed/excluded changes, verification, resource limits, and expected handoff. Specify read-only versus implementation work. Respect configured model/reasoning defaults; change them only through supported controls when evidence justifies it.

#### Coordinate safely

Use only capabilities actually available. Never assume visibility into other chats, shared memory, automatic messaging, workspace isolation, or persistent monitoring. Distinguish prepared assignments from dispatched work and observed status from assumptions. When delegation is unavailable — the session has no way to spawn a worker — work directly or provide an explicit handoff.

Isolate concurrent edits in a worktree: a session or agent doing anything beyond a trivial read works in its own worktree by default, because two sessions in one tree invalidate each other's comparisons, gates, and commits. Serialize overlapping writes only when a worktree is genuinely unavailable, and say why. Finishing a worktree means merging its branch to main and pushing, in the same session — a worktree is never where work is left to sit. Remove it with `git worktree remove` once its branch is merged; a worktree still on disk after its work has landed is a defect to report, not housekeeping to defer, and a session that ends with one says so and where it is. Account for shared services, databases, ports, and compute limits. Never overwrite or discard another participant's work. Track delegated work through completion, cancellation, or handoff, and release only resources you own without losing work.

#### Preserve state and decision boundaries

Keep essential memory in the repository or existing tracker, not conversation history. Reuse conventions and maintain only useful documentation. Record owners, dependencies, revisions, status, blockers, and consequential decisions. The coordinator owns canonical status; workers supply scoped updates. Explicitly propagate changed contracts and revalidate stale information.

Distinguish intended requirements from actual behavior. Preserve evidence, unresolved issues, and next steps at handoff or interruption. Exclude secrets and unnecessary private data.

Workers act autonomously within scope. Escalate cross-task interfaces, persistent formats, security boundaries, major dependencies, and scope changes. The coordinator resolves these within the approved mandate. Unapproved major architecture/product changes and consequential external actions require human authorization. Continue safe independent work while blocked.

#### Implement and verify

Inspect, implement a coherent increment, run relevant checks, diagnose, fix, and recheck. Preserve established architecture; avoid unrelated rewrites, speculative abstractions, and unnecessary dependencies. Proceed beyond planning when implementation is requested.

Use task-appropriate evidence and establish baselines when needed. Inspect actual user flows for interactive products. For games/simulations, check relevant invariants, save compatibility, and realistic-scale performance. Prototype uncertain ideas before generalizing. For research, cite evidence and distinguish hypotheses, measurements, and conclusions.

Obtain independent, preferably read-only review for substantial or high-risk changes when available. Review the exact revision against acceptance criteria. Evaluate findings, fix justified issues, and rerun affected checks. Never weaken tests or conceal failures to claim success.

#### Integrate, report, and stop

Workers hand off outcomes, changes/revisions, checks and results, risks, blockers, and integration requirements. The integration owner inspects actual changes, integrates in dependency order, and verifies the combined result. Worker success alone does not establish integration success. Respect merge, push, deployment, and publication permissions.

After two failures for the same reason, reassess rather than repeat. Unless another budget is specified or the user authorizes continued work, cap automatic repair at five substantive attempts, then report evidence, blockers, and next steps. An explicit user override remains in force for its stated scope; do not ask to renew an overridden default cap.

Keep updates brief and decision-relevant. Clearly distinguish implemented, verified, reviewed, integrated, and blocked work. Stop when acceptance criteria and material findings are resolved; do not invent follow-up work. Report partial completion and unavailable verification honestly.

#### Final acceptance gate

The integration owner is accountable for final acceptance. Before reporting completion:

- Check every acceptance criterion against the final integrated revision, using actual changes and verification evidence—not worker summaries alone.
- Run relevant automated checks and exercise affected end-to-end behavior. Check cross-task interactions, not just each task in isolation.
- For substantial or high-risk work, obtain an independent read-only review of the integrated changes, including integration fixes. If unavailable, explicitly report the missing review rather than implying it occurred.
- Resolve material findings, rerun affected checks, and obtain focused re-review where fixes invalidate earlier review.
- Report the verified revision, checks and results, review status, and any failed, skipped, or unavailable checks. Mark unmet criteria as incomplete.
- Confirm the verified revision is merged to main. Report anything left on a branch or in a worktree, and where it is.

Do not declare the result fully verified while material findings or required checks remain unresolved. Respect the repair budget and report blockers.

### Fleet conventions

- Repository rules add concrete local constraints consistent with the Fleet Orchestration Policy; they do not override its permissions, adaptive workflow, or stopping limits.
- Verify visual work visually: capture the rendered result — screenshot, frame, recording — and look at it, because a passing test says nothing about what the pixels do. Work with no visual surface runs headlessly. For 3D work, one framing is not a check: sweep several camera angles and zoom levels, since a defect the chosen view happens to hide is the normal case. For 2D interfaces and artwork, inspect relevant viewport sizes, scales, and states. For games and other interactive visual deliverables, exercise real controls and representative user flows, and inspect how the rendered result responds over time. For static scenes and assets, inspect applicable viewpoints, using orbit, pan, or zoom in a viewer when available and useful. Use headless interaction and rendering when they provide adequate evidence; use a visible session only when necessary to verify behavior. An aggregate view — a contact sheet, grid, montage, or proof sheet — answers "is there one of each" and never "is each one right", and answers the first just as confidently when the second answer is no: inspect each item at the artifact's own native resolution, and bind the review to the digest of the bytes inspected, so regenerating the artifact strands its review instead of inheriting it. Badge's 63-source contact sheet read as cohesive while ten sources were wrong, and the lesson recurred four days after it was written down, against 48px proof sheets. For visual tasks, inspect the affected user flows and the surrounding rendered result for material regressions; choose the coverage from the change's risk and acceptance criteria. A harness that sets state directly — assigning the camera pose, calling the render function, writing the store — is not exercising the controls, and is structurally blind to every defect living in the input path it skipped, while reporting confidently on the path it kept. scenes applies a camera clamp each frame after the damped controls have run; a diagnostic that assigned camera positions and rendered could not reach the defect the user was reporting, measured the wrong thing, and was used to call it fixed while the user was still watching it happen.
- A defect the user reports is recorded and gated, never only fixed: an entry in `docs/learning/defect-register.md` — symptom as they saw it, investigation, root cause, and how it is checked from now on — plus a check that covers the defect's whole class rather than the one instance. Unlike a lesson, the entry stays after it becomes a gate: the register is the standing list of what the gates could not see, which is where the next defect comes from.
- Gates pass before any commit that touches code; a dependency change re-runs the audit gate. The user has authorized committing, merging to main, and pushing in every repository they own, with no separate approval each time — that standing grant is what the policy's merge and push permissions resolve to. Force-pushing, rewriting history, deploying, and publishing still need the user's authorization.
- For an authorized push, inspect the remote gate through completion when available. Read job steps and runner assignment before treating a failed run as a code failure: exhausted Actions allowance can fail before any job starts. Report unavailable remote verification and use the local gate as evidence within its bounds. Resolve failures that block the requested outcome within the repair budget; report unrelated failures without silently expanding scope.
- The user archives threads, and anything sitting outside main is thrown away with them. So work counts as done only once it is merged to main. A branch, a worktree, or an uncommitted tree does not count, whatever its gates say. Merging is the last step of the work. If something cannot be merged, say so and say where the work is.
- A repo chooses its own language and toolchain — Node, Python, and Rust all run here. Each pins its version where its own tooling reads it (`.nvmrc`, `requires-python`, `rust-toolchain.toml`) and names it in Gates, so a version mismatch is not read as a code failure. Node repos baseline at 24; an older major keeps a CI job proving it.
- Runtime model calls are authorized and already paid for — this fleet has one user, with Claude Code and Codex subscriptions — so a program here may call a model at runtime, vision included.
- When a hard problem blocks progress, use `../fleet/docs/skills/hard-problem.md` to explore distinct approaches. Give each idea a newly spawned independent owner and only the context needed to learn the domain and test assumptions from first principles. Queue waves within available resources; compare evidence before combining routes. Before abandoning a whole strategy, prove it cannot meet the user's requirements under stated assumptions, and obtain independent scrutiny of that proof.
- For substantial or high-risk changes, use independent review when available. High-risk areas include persistence/migrations, security/auth, concurrency, money, supply chain, and edits that reach sibling repos; `../fleet/docs/skills/multi-cli-review.md` provides the review mechanics.
- Error messages are a product surface: check the affected class and relevant adjacent paths. Each names what happened, which input caused it, and what would satisfy it — never a bare `Validation failed`.
- When blocked, hand over the relevant artifact — screenshot, rendered page, log line, data row — with secrets and unnecessary private data removed, as soon as the blocker is named rather than after the analysis: your description of it is filtered through the misunderstanding that caused the block, so it cannot contain what you failed to notice.
- Task-run evidence lives only under ignored paths and is deleted once no active task, unresolved issue, or handoff needs it; it enters Git only when review promotes it into a repository input — a fixture, golden, snapshot, or contract. Tracked docs keep plans, authored review reports, conclusions, and provenance; raw task output stays ignored. Blob ceilings for anything promoted: over 256 KiB needs a stated reason, over 512 KiB binary or 1 MiB of anything never enters ordinary Git, and an asset store or LFS needs the user's approval.
- Keep planning documents and every authored review round in a permanent `docs/work/<id>_<theme>/` folder, with consecutive IDs from 0 independently in each repo. `plan.md` holds status; shared documentation stays in its canonical home. Allocate through the repo's common authority and follow `../fleet/docs/work-docs.md` for formats, review targets, and migration.
- Use the common word where it says the same thing as the rare one. This covers chat, docs, commit subjects and PR titles, comments, and error messages. One idea per sentence, unless another rule asks one line to carry more. Cut length, not facts: keep exact terms, numbers, and the evidence a claim rests on. It applies to sentences you write, not to text you quote or paste. Do not copy this canon's style.
- Write prose one line per paragraph (no hard wrapping).
- Keep a devlog: one short dated line per behaviour-changing session in `docs/devlog/summary.md`, newest first, and a section in `docs/devlog/detailed/` for anything a later session could trip over — what was believed and proved false, what a reviewer caught that the author missed, what number moved and from what. It is history, not status. Both shapes are in `../fleet/docs/devlog-template.md`.
- A lesson is prose only until it is a gate. It lands the session it is learned in `docs/learning/lessons.md` — read at session start — anchored to a measurement, commit, or test id, and naming the gate that will retire it: a test, a lint rule, a schema check, a fixed command. That file is a queue: an entry is deleted in the commit landing its gate, and a gate counts only once it has been made to go red by reintroducing the defect. Deleting the prose is safe only because the deletion is recoverable, so the gate carries the claim in its own header and `docs/learning/gate-proofs.md` carries the mutation, the failure it produced, and the pre-retirement commit that `git show <sha>:docs/learning/lessons-evidence.md` reads the whole evidence file back out of. A gate and the claim in its header can be wrong together and look exactly like a gate that is right, and auditing one means reaching what was believed, measured and abandoned at the time — never the sentence the gate carries about itself. An entry that can name no gate is not a lesson — fleet-wide knowledge is staged in `canon-candidates.md` for this constitution, repo-only knowledge goes to `docs/policies/local-rules.md`, and the rest is folklore and is dropped. An index that only grows is a list of things that failed to graduate: aoe2's reached 84 entries, none naming a gate. An index already holding ungated entries is emptied entry by entry as each one's area is next touched, not kept as a standing exception. Shape: `../fleet/docs/lessons-template.md`.
- A green gate proves less than it looks like. Every gate is bounded by something — a seed set, a tick window, a resolution, a fixture that ends early, an include list, a shared flag any one case can satisfy — and proves nothing past that bound, so name the bound in the gate's own header and pin every input that reproduces the defect, not just the one you thought of. Past its bound a gate does not merely miss the defect — it can measure a different phenomenon entirely and report it just as confidently: aoe2's stone-mining window opened at tick 11,000 on a fixture that resolves by conquest at 11,442, so it was reading a decided match, and a finished match and a deadlocked one are pixel-identical. A gate that cannot tell "passed" from "did not run" reports the second as the first, and a check built from the same symbol as the thing it checks proves only that the code agrees with itself. Retiring 356 lessons across 14 repos found **more than 40 whose evidence named a live, passing test that did not catch the defect** — every repo's `docs/learning/gate-proofs.md` records its own: an 800-decision rollout window hid a divergence that starts at 3,000, a Rust-side struct pin stayed green while the WGSL side it mirrors gained a field, and `replaceFootprintOwner(…, undefined)` passed all 873 tests.
- A command's exit status is a claim about the command, not about the work: a pipeline exits with its last stage's status, so `npm run x | tail` reports tail's success over any failure; `git add` fails all-or-nothing while the `commit` after it still succeeds and ships a message that lies about its contents; and a tool reporting that it applied a fix reports a no-op identically to a refusal — read the artifact it should have changed. Red deserves the same suspicion as green: a non-zero exit is equally a claim about the command, and a missing dev dependency, an unresolvable binary or a wrong working directory fails identically to a broken product — aoe2's `playtest:corpus` went red on a merge because `tsx` was gone from `node_modules`, not because the code was wrong. A blocker you inherited is the same kind of claim: retest it before repeating it, because its whole effect is to stop work. A RETURN VALUE is a claim of the same kind: a search that cannot match hands back a sentinel the next call uses without complaint, and an `indexOf` miss fed to `slice` deleted 319 lines of a tracked spec in one edit.
- Verify the instrument before trusting the measurement, because a critic is a backstop and not the first line. Confirm the flag took effect, the denominator is the population you meant, the control reproduces, and the claim you are relying on is still true rather than remembered. A whole session's conclusions were built on labels chosen with knowledge of the future, agreement quoted over a population that was 99.8% forced no-ops, a `--eval-episodes` flag silently ignored so every checkpoint was picked by a five-sample lottery, and a review lane declared unavailable from a three-week-old memory that was wrong. Each was one command away from being caught. An A/B comparison asks one more thing: that the tree HOLD STILL. Edits landing between the two arms make them differ by more than the variable under test, and the result reads as a finding — aoe2 read a boot-map regression off two arms it had edited between. A repo that ships a debugging instrument — a session replayer, a recorder and bundle differ, a capture script, a profiler, a debug probe — is asked FIRST, and the task's first probe names which of them answers the question or why none does. aoe2 skipped its engine's replay harness twice with the rule in prose (2026-06-13, 2026-09-05), the second time with a memory stating the rule loaded in the same session; what held was a hook that refuses to write or run a scratch probe without a `harness:` line naming the tool. A rule that must be remembered at the moment of writing a probe is enforced at that moment, not read at session start.
- Anything slow on the critical path is a defect to identify and fix, not a cost to schedule around (owner directive, 2026-09-15). Keep only the slowness a verdict depends on. What remains is the expensive gate the team is sized around (scenes: every gate ran through a CPU rasterizer on a machine with a GPU, a fourteen-second frame on every round-trip).

- A standing loop sources its next task by running the artifact the way its user does — the default entry point, the real configuration — never by reading code for something to improve. A repo with no runnable entry point has no standing loop.
- This harness compacts context mid-task: a compaction is a harness event, not a task boundary, and never a reason to wrap up or hand off to a fresh session.

- Before resuming interrupted work, inspect surviving worktrees, artifacts, and task status. Recover what exists and preserve unfinished work; do not assume that a worktree, transcript, or shared memory survived.

- Steering compounds: a direction that outlives the immediate task lands that same session — `../fleet/FLEET.md` if fleet-wide, else this repo's `docs/policies/local-rules.md` — and you say where it went.
- Reviewer model pins live only in `../fleet/docs/skills/multi-cli-review.md`; a model a product itself calls is pinned in the repo that calls it. Never hardcode a model ID anywhere else.

## Gates

- **Node 24**, pinned by `.nvmrc` and `engines.node`; run against v24.18.1. A version mismatch is not a code failure, so check it before reading a red gate as one. Playwright's chromium must be installed once (`npx playwright install chromium`). The gates need the network: every page fetches the fonts from Google Fonts and the 3D figures fetch the pinned Three.js from jsdelivr, and a failed request is a failure.
- **`npm test` is the gate**, and it passes before any commit that touches code. `tools/test.js` runs thirteen steps as separate processes, cheapest first, with no pipe anywhere, and stops at the first red one, naming it: `npm run unit`, `npm run check`, `npm run theme`, `npm run shot`, `npm run flow`, `npm run drive`, `npm run pinned`, `npm run sitting`, `npm run narrow`, `npm run legible`, `npm run devices`, `npm run sweep3d`, `npm run subpath`. Each is also runnable alone, and each states its own bound in its file header. A trimming variable (`THEME_PAGES`, `SHOT_PAGES`, `SHOT_VIEWPORTS`, `SHOT_THEMES`, `DEVICE_PAGES`, `DEVICE_ONLY`, `DEVICE_ENGINES`, `DEVICE_THEMES`, `DRIVE_KINDS`, `PINNED_KINDS`, `NARROW_KINDS`, `NARROW_THEMES`, `LEGIBLE_KINDS`, `LEGIBLE_THEMES`, `SWEEP_KINDS`, `SITTING_THEMES`, `SUBPATH_PAGES`) that names nothing that exists stops the gate naming the valid values (`tools/lib/trim.js`), rather than running nothing and passing; page ids are book-qualified (`biology/ch01`, not `ch01`).
- **`npm run unit`** (`node --test "test/*.test.js"`) covers the content checker on fixtures, the palette's two copies staying equal, the one element table (`src/figures/lib/chem-atoms.js`) against the CSS colours `lib/mol-draw.js` derives from it and against the chapter-2 brief, the registry against the modules on disk, the page list against the chapters on disk, what the Pages trim would leave a reader able to fetch (`test/publish.test.js`: no Markdown survives, a brief in a chapter that does not exist yet is already excluded, the site itself survives, and both consumers still go through the one matcher), every figure module read as text for a binding used before its own `let` or `const` and for a name nothing in the module declares (`test/use-before-declared.test.js`: `if (x)` on a binding declared below it throws rather than skipping, and `x?.set()` hides it better — it sees no closure and nothing dynamic, and says so), the scheduler and the progress store, that no multiple-choice question, in Today or in a chapter's checks, gives its answer away by where it stands, while an answer in Today still records the option's own authored letter (`test/choice-order.test.js`: a chi-square bound over every bank and every check on disk, driven through the two components' own render and answer paths; a check's order must also be the same at the root and under `/textbook/`, and one id on two pages must draw two orders), and the homeostasis model's recovery and drift. The glob is deliberate: `node --test test/` on Node 24 reads no test file at all — it makes one bogus test named `test` and fails it with `ERR_UNSUPPORTED_DIR_IMPORT`, so a run that touched none of the suite still prints a test count (measured on 24.18.1, 2026-09-16). How many tests there are is not written here: the number has been wrong twice, and the claim that matters is that every file matching the glob runs.
- **`npm run check`** reads every page's authored HTML and the data beside it. The prose: registered kinds, unique ids, captions and alts on every figure, every term in the glossary, every entry used and no markup in an entry's term (a term is set as text, so a tag in it is printed), one correct answer per check, bins and reasons on every sort item, heading order, every figure cited in the prose, resolvable hrefs, no TODO. The study data (`objectives.js`, `items.js`): every question names an objective the chapter declares, every prerequisite resolves, the prerequisite graph has no cycle, every objective is taught by a section and figure that exist, a chapter that declares objectives has an item bank at all and at least three items test each objective, every distractor carries the misconception it encodes, and every figure task names something that can grade it. It also runs every figure task's `expect` through the grader's own parser (`expectProblems` in `src/components/task.js`) and fails a clause no figure state could satisfy, and it fails when a chapter has an `items.js` that `today/index.html` lists no `tb-source` for. It fails a check's explanation or option, or a multiple-choice item's explanation, option or why, that names an option by where it is written ("the last option", "option B", 「前两个选项」), because every reader sees the options in a drawn order; the phrasings it knows are listed in `OPTION_POSITION`, and "the last is wrong" is not among them.
- **`npm run theme`** loads every published page that loads the shell, found by following each page's scripts and their imports to `src/shell.js` (`tools/lib/shell-pages.js`, so `lab/` is in and a new page is found without anyone listing it), in seven situations: a stored theme opposite to the emulated system preference, each way round; `?theme=` opposite to it, each way round; nothing chosen; and `localStorage` refusing a read, or refusing access at all. It fails when `data-theme` on `<html>` is not the theme the page is to be drawn in at any moment from `<body>` being inserted to the handshake, or is not the value the shell leaves there — read from the order of the records a MutationObserver installed by an init script collects, so no timing enters the verdict — when a load stores `?theme=` or changes the stored choice, and when the page, storage throwing or not, does not reach the handshake showing its content with no error. It exists because `src/shell.js` applied the reader's theme only after the page had been styled once, so a reader whose stored choice differed from their system saw the whole page in the other theme for one to three frames and then its titles fade across (`docs/learning/defect-register.md`, 2026-09-22). The fix is `THEME_BLOCK` in `src/theme-early.js`, a classic script every such page carries in its `<head>` before its first stylesheet, and `test/theme-early.test.js` in `npm run unit` holds each page's copy as text: it fails a page missing the block, carrying a drifted copy, or carrying it after a stylesheet, and prints the block to paste. Bound: Chromium only, one viewport, and the attribute rather than the pixels, so a block moved to the end of `<head>` still sets it before `<body>` and passes here (the unit test fails it), and a flash in the right theme, a late stylesheet or font, is not seen. `THEME_PAGES` trims it.
- **`npm run shot`** loads every page at 390, 1024 and 1440 px in both themes with `?eager=1&t=0`, fails on any console error, page error, failed request, figure in `error`, or horizontal overflow, and, on a page whose `lang` is English or Chinese, on a figure caption or `aria-label` whose word is not in the page's script (`Figure`, `图`, `圖`), and writes `out/shots/`. Before the shutter opens it waits, one animation frame at a time, for every CSS transition, CSS animation and Web Animation on the page to finish, and fails a page still moving 120 frames after its audits, naming what moves. It also reads back every geometric attribute the mounted figures wrote into the settled DOM and fails one that is negative where SVG forbids it or is not a finite number, naming the kind, the element and the attribute: the console-error check above it catches only what the browser complains about, and `stroke-width="NaN"` is dropped in silence, so the two halves of that class needed two checks. It fails a reader component's text box that is narrower than its own longest word, a sort name that wraps in less than 15 em a line, and a sort whose rows split between two layouts (the text-box block in `tools/shot.js` names the subjects; it presses nothing, so a popover is outside it). It also takes a font census per page load: every text node and `::before`/`::after` string is grouped by its computed stack, weight, style and numeric variant, a probe span per group is measured through CDP `CSS.getPlatformFontsForNode`, and a character drawn by a face the page did not load through `@font-face` fails, narrowed down to the code point and named. What counts as chosen is read off each page, so `tongjian/**`'s Noto Serif SC and Noto Sans SC need no entry and a third book's stack will not either. It cannot be asked once for the page — Chromium walks two levels below the node it is given, so `<body>` reported 19 glyphs on a chapter of 1316 text nodes — and it cannot see text drawn into a canvas, a character that appears only after a control is pressed, or `lab/`, which this gate does not visit. The Today frame is a photograph of a booted study page because **the handshake now covers `<tb-sitting>`** (see the invariant below), so this gate inherits the wait and no longer keeps one of its own; what it keeps is the census, which says the three things the handshake cannot — that the page whose subject that is still carries a `<tb-sitting>` at all, since the handshake's term is vacuously true on a page that lost the element; that the shell still exposes `describeSittings()`; and that every sitting reads back booted **after** the handshake resolved, which is what goes red if the term is deleted from `_check()`. Until 2026-09-17 the handshake said nothing about that element, whose boot imports each chapter's `objectives.js` and `items.js` and then fetches its `index.html`, and this gate's Today frame was a coin toss: two runs with nothing between them differed on 3 of 6 frames, 102,349 bytes against 163,667 for the same frame, and the short one showed none of the study surface. Its frames are for a person to look at, and they are **not byte-reproducible**: three full runs of one still tree on 2026-09-23 wrote 61 of 72 frames identically, and the other 11 differ through SVG label advances, `backdrop-filter`, a figure stage's rounded corners and one unexplained 21-pixel speck, which `tools/shot.js`'s header measures one by one. A hash or a byte comparison of `out/shots/` is not a regression signal. `SHOT_PAGES`, `SHOT_VIEWPORTS`, `SHOT_THEMES` trim it.
- **`npm run flow`** drives the reader controls on the chapter through real mouse, keyboard and drag input: the checks, the sort, a glossary popover, the theme toggle, the phone contents drawer. It presses a check's option by `data-correct`, never by its place, because the order is drawn; so a check that marks the wrong option correct passes it, and `npm run unit` is what sees that. Its screenshots are taken the instant after a press, while an answered option's tint is still in its CSS transition.
- **`npm run drive`** drives every figure's own controls in the lab the same way, one recipe per kind in `tools/drive.js`, asserting what `describe()` reports afterwards; a kind with no recipe fails, and so does a kind whose `describe()` uses one of the four names the frame owns (`id`, `kind`, `number`, `state`), or one the frame holds no handle for or whose handle has no `describe()`. `DRIVE_KINDS` trims it. **A recipe waits by polling, never by sleeping** (`docs/policies/local-rules.md`, "A wait in a gate must poll the artefact, never the wall clock"): `until` polls `describe()`, `atValue` waits for a control to carry the value the figure has already published, `atLeast` waits for the DOM the assertion is about to count, and `stable` waits for a figure to stop moving. A fixed sleep survives only where the elapsed time IS the measurement — where the step's claim is that something did *not* happen while time passed — or where it is letting an animation settle before the step's `out/drive/` screenshot; each of those is commented where it stands, and the file header lists them.
- **`npm run pinned`** is `drive`'s pair from the opposite side: it opens the lab at `?t=0`, works every control every figure has — every visible button, every slider driven by End, Home and PageUp on the control itself, every focusable sent the named keys and the ones its own label documents — and fails a figure still changing across an untouched window of animation frames afterwards. It is what `npm run shot` rests on, since shot photographs every page pinned and presses nothing. One action per fresh mount, deliberately: the first version pressed a kind's controls in order on one page and reported green over the very defect it was written for. It **runs as shards** — `PINNED_SHARDS` processes of the same file, eight by default, each given its slice through `PINNED_KINDS` — because the kinds are independent and because this gate counts animation frames rather than milliseconds, so a loaded machine cannot change a verdict. One command, one verdict: any shard that exits non-zero, dies on a signal, or exits 0 without printing its totals record fails the run, and the summary sums the shards so a reader sees the same counts a single process printed. `PINNED_SHARDS=1` is the reference run. Measured 2026-09-17 on 32 logical CPUs, three arms on a tree hashed still: 410 s at 1, 80 s at 8, 73 s at 16, with kinds, mounts, presses and keys identical in all three (`docs/learning/gate-proofs.md`). 8 is past the knee, not a ceiling.
- **`npm run sweep3d`** renders each WebGL figure at fourteen light views and one dark view through `setView` and fails a frame that is near-black, flat or blank; `out/sweep/` is for a person to look at, because the gate detects an absent frame, not a wrong one. It measures the bare canvas with every HTML overlay hidden: measuring the whole stage passed a figure whose renderer had been replaced by a clear, because the labels and buttons varied enough to look like a frame.
- **`npm run narrow`** mounts every figure at a 390 px stage in both themes and fails one that does not reach ready, draws a blank, flat or near-black frame, or has no control left to press. It then **opens what a reader can open** and measures the opening state and every state a press reaches: the toolbar may not take more than 55% of the stage's height, and on a figure built on `src/figures/lib/bench.js` no pane's drawing may land on another pane's drawing or on a control. A disclosure cannot be read off the markup — the bench has no disclosure primitive and `enzyme-kinetics` builds its two out of `b.toggle` plus `style.display` — so one is found by trying: every visible enabled `button` in the figure's `.fig-toolbar` that carries `aria-pressed`, pressed once in DOM order, pressed again if the press hid controls, the toolbar re-read each round. That was added on 2026-09-17, after a worker found `enzyme-kinetics` at 390 px with a ten-row 320 px toolbar over a 456 px stage and its graph drawn over its readout — two presses from the opening state this gate was the only one measuring, which is the "fixture that ends early" shape. Bounds, printed on every run: an action button is never pressed, so a disclosure with no `aria-pressed` and all its crowding is invisible (**demonstrated**, not asserted, in `docs/learning/gate-proofs.md`); the search is greedy, not exhaustive, so a state needing two presses in the other order is not visited; the two collision checks read only the 9 bench kinds of 44, because a pane grid with the toolbar's measured height as its bottom padding is a promise only the bench makes and for the other 35 a toolbar over the artwork is the design; and a drawing that runs off the stage is clipped by `overflow: hidden` rather than landing on anything, so it is invisible here too (**also demonstrated**). Five figures carry a second composition for a narrow stage, and before this gate none of that code was covered by anything. It writes `out/narrow/` at three times scale, because legibility is the reason those layouts exist and no measure judges it, plus `-opened.png` for the widest state each sweep reached and `-crowd.png` for the state that failed. `NARROW_KINDS` and `NARROW_THEMES` trim it.
- **`npm run legible`** measures the contrast of every glyph a figure puts in the DOM against the pixels actually under it, in both themes, at a 1000x640 stage, in the figure's opening state and after each of its own visible enabled buttons has been pressed once. WCAG 2.x AA — 4.5:1, or 3:1 where the glyph is RENDERED at 24 px or more, which is not the declared size: a `font-size: 40px` letter inside one of `levels`'s thumbnails is six device pixels on screen. It exists because the fills in `src/palette.js` and `src/figures/lib/cell3-colours.js` do not move with the theme while `ink` and `paper` do, so type over one of them is right in one theme and unreadable in the other, and blankness — which is what `npm run narrow` and `npm run sweep3d` measure — is exactly what pale type on a pale fill passes. Each state is rendered three times, as it is, with every measured glyph transparent, and with every measured glyph magenta: the magenta frame is the glyph mask, because a mask read off the figure's own frame would be circular — text the same colour as the fill under it changes no pixel, and the defect would read as "this text draws nothing". Bound: one stage size, so the narrow compositions are `npm run narrow`'s; the opening state plus one press per button, so a pair only a slider or a click on the drawing reaches is not seen; only text in the DOM, so a glyph painted into a canvas or by WebGL is invisible and the canvas count is printed per figure; the surface is the WORST pixel under a glyph's core — every core pixel is given its own ratio and the glyph's is the one at least 95% of them beat, so the reported number is a real surface rather than a named one, and a gradient, a texture and a label straddling two fills are all in range. The 5% set aside is where a hairline rule crossing a stem lives; antialiasing cannot get into it, because a blended pixel's ratio lies between those of the two surfaces it blends. Until 2026-09-17 the rule was a dominant colour under at least 40% of the core pixels, and 44 of `bondlab`'s 48 element symbols were skipped as "varied ground" while the gate reported one problem for a figure whose every O, N and S was below the bar — every line now prints how many of its runs stand on ground that old rule could not have named. A disabled control is exempt, as WCAG 1.4.3 exempts it; and a state that will not hold still is named as NOT measured, with a kind that has no measured state at all failing the run. `ALLOWED` in the file is the list of pairs the book has looked at and not yet decided — every entry carries the ratio it was measured at and stops applying if the pair gets worse, every one spent is printed on green runs too, and an entry nothing spends fails a full run. `DEFERRED` is the list of whole figures it does not visit yet — chapter 4's eight and the second book's three, each with the count measured on the day the gate was written and the reason — printed in full on every run and failing the run if a name there is no longer a registered kind. `LEGIBLE_KINDS` and `LEGIBLE_THEMES` trim it.
- **`npm run devices`** emulates nine real devices — small phone, phone, Android phone, phone landscape, tablet in both orientations, small laptop, desktop and wide desktop — with touch where the device has touch and a mouse where it does not, and presses the controls it checks — the contents button, one link in the drawer, every glossary term, a tap outside the drawer — with the input that device actually has; it presses no check option, sort control or figure control. It checks sideways scroll, the header controls being on screen and at least 24 px and truly in the corner, the contents drawer's scrim, scroll lock, focus, outside-tap and link dismissal, **every** glossary popover staying on screen, and the text column and the wide figures each keeping to one pair of edges. A suite that finds none of its subject on a page that must have it — the header on every page; the rail, the glossary terms and the text column on a chapter page — fails naming the selector and the page, from a per-page table in the file, rather than skipping. Every other gate here sets a narrow viewport on a desktop browser, which has a mouse, hover and `pointer: fine`; three of the four defects the owner found on a real phone lived in exactly that gap. `DEVICE_PAGES` trims it. Bound: a page is loaded on one device per *shape* it can exercise — the layout band its width falls in, together with the input its controls are pressed with — rather than on all nine, and the run prints the matrix it derived before it loads anything; `DEVICE_ONLY=phone,phone-android,tablet,desktop-wide` puts the old whole-matrix run back. The derived matrix re-runs on WebKit and Firefox for the two shapes either side of the drawer breakpoint over the library and chapter 1, which between them carry everything this gate checks — not Today, whose study surfaces are `npm run sitting`'s and run on Chromium only — and Firefox's phone arm is a narrow touch viewport rather than a device, because Playwright cannot emulate one there. `DEVICE_ENGINES` and `DEVICE_ONLY` trim those. This gate does **not** pass `?eager=1`, so the handshake here is the shell plus the sitting term and not the figures; before that term it raced Today's boot and photographed whatever had finished — three `DEVICE_PAGES=today` runs with nothing between them wrote the tablet-landscape frame at 109,658 bytes once and 193,829 twice, the short one carrying none of the study surface, and the gate called every one of them clean. A handshake that times out now prints the sittings beside the figure states, so a page held by an unbooted sitting says so instead of showing an empty figure list. **Every load but one pins the figure clocks (`t=0`)**, which is 6.6× faster because a Playwright action on a page of nine animating figures waits for the element to hold still across frames; the cost is that animation-induced layout shift is watched at **one device shape, not nine**, and the run's `running:` line says which load that was — the smallest phone on a chapter page — or says that a trimmed run reached none.
- **`npm run sitting`** completes a study sitting on the Today page with the keyboard alone, in both themes at two widths, from a record it clears first. It fails when a question cannot be answered, when an answer records no objective, no format or no chosen option, when a recorded `chose` is not the bank's own letter for the option whose text was on the button pressed (answered by Enter and, every other question, by the letter printed on the option, at a position where the screen's letter and the bank's differ), when the sitting has not reached its end summary within 24 presses (read from `tb-sitting.describe().finished`), when that end summary carries no per-objective label at all, or when a label anywhere on the page claims more than the record supports. That last one is the reason it exists: the page once said "Learned well" after one right answer, while the store said `learnedWell: false`. The word, the label's class and the end summary's class are read from `src/components/mastery.js`'s exports (`LEARNED_WELL_WORD`, `MARK_WORD_CLASS`, `CLOSING_CLASS`), not from literals, so rewording, translating or renaming moves the check instead of emptying it; the "at least one label" claim is made of the end summary alone, because "Where you stand" renders labels before any question is answered; and every line prints how many labels it read, because `0 label(s)` is a run that compared nothing.
- **`npm run subpath`** rebuilds the tree GitHub Pages actually publishes, from the one exclusion list in `tools/pages-exclude.txt`, serves it under `/textbook/` and loads every page there at two widths in both themes. It fails on a root-absolute path, a same-origin 4xx, a request that escapes the subpath, a figure that is not ready, or horizontal overflow. The site deploys from `main` on every push, so "it works at the root" is not the claim that matters. The list holds **patterns**, not a roll-call: `**/*.md` is what keeps every chapter's `FIGURES.md` off the live site, because naming them one at a time had already published two and would have published chapter 4's. `tools/pages-exclude.js` is the one matcher — this gate, the Pages workflow (`node tools/pages-exclude.js --print0 | xargs -0 rm -rf`, since neither `rm` nor `xargs` expands a glob) and `test/publish.test.js` all go through it, so the three cannot disagree about what a pattern means. It inherits the handshake's sitting term, so its Today frames are reproducible; before that term three runs of `SUBPATH_PAGES=today` on a tree hashed still wrote `today-desktop-dark.png` at 102,349, 163,667 and 50,734 bytes. `SUBPATH_PAGES` trims the page list, and because a trimmed run is not a site-wide verdict the last line names the pages it judged and the pages it did not.
- **The gates fetch each external URL once a run, not once a page load** (`tools/lib/net-cache.js`, installed inside `openPage`). The fonts from Google and the pinned Three.js from jsdelivr are still fetched over the real network — the first request for each URL in each gate's process — and every later request for the same URL is replayed from that run's memory, keyed by URL *and* user agent so three engines never share one stylesheet. Nothing is written to disk, so a run cannot pass with the CDN down: an unreachable URL still fails the run, on the first load, through the same `requestfailed` path. What it stops proving is that a CDN URL is reachable on *every* page load — about ten proofs a chain instead of three hundred. It is worth 130–250 ms a load and about 50 s of `npm run shot`; `NET_CACHE=0` turns it off, which is how that was measured, and every run prints how many URLs it fetched and how many requests it replayed so a cache that did nothing says so.
- **`npm run audit`** (`npm audit --audit-level=high`) is the dependency-audit gate; re-run it on any dependency change. It sits outside `npm test` because it reaches the registry.
- Not gates: `npm run perf` (frame time and draw calls on the machine it runs on), `npm run figure -- <kind>` (one pinned frame of one figure), `npm run inspect <page>` (viewport frames at named elements), `npm run review` (what the reader's study record says, calling no model), `npm run progress:export` and `npm run progress:import` (the record's backup and the way a sitting read on a phone reaches the agent). These are the instruments; a scratch probe names which of them it stands in for.
- Every gate is proved red before it counts, and the proof is in `docs/learning/gate-proofs.md` — **read that file's index and the one entry it sends you to, never the file**, which is dozens of proofs and runs to hundreds of kilobytes. A green run proves what the header says and nothing past it; the screenshots the gates write are the check for the pixels, and the person who looks at them says so in the work folder's plan.

## Invariants & boundaries

- **A figure that can fill any shape declares a `narrowAspect`, and one whose type would shrink below about nine device pixels on a phone carries a second composition rather than a scaled-down first one.** `npm run narrow` covers that second layout; a figure gaining one without a gate is how five of them nearly shipped unwatched.
- **A figure is a module with the contract in `docs/design/textbook.md`**: `meta`, `mount(root, ctx)` returning `destroy`, `setTime`, `describe`, `setVisible`, and for 3D `setView` with a non-zero `view.distance`. The frame (`src/components/figure.js`) is the only thing that mounts it, and the gates drive it only through that frame and its own controls.
- **The frame owns `id`, `kind`, `number` and `state` in `describe()`; a figure may not report a field with any of those names.** They are spread last so the frame always wins, and `npm run drive` fails a figure that uses one, because winning silently would drop the figure's own value without a word. `foldlab` reports `foldState` for this reason.
- **Every frame is a pure function of its clock and the reader's actions.** `setTime(t)` pins it; nothing advances on its own while `ctx.pinnedTime` is set; no `Math.random` in a figure, only a seeded generator. That makes a figure's state and drawing the same every run; it does not make a gate's screenshot the same bytes every run, which it is not (`tools/shot.js`'s header says why, and what the frames are for). Nor may a figure's frame depend on when a webfont arrived. The figures known to break this invariant are recorded in `docs/learning/defect-register.md`.
- **One colour table.** `src/styles/tokens.css` and `src/palette.js` hold the same values and a test fails when they drift; figures colour from `ctx.palette` or the CSS variables, never from a hex of their own.
- **No build step, no bundler, no framework, no raster images, no downloaded models.** Three.js arrives only through the import map, at the version pinned there. A dependency added to `package.json` is a decision recorded in the design doc.
- **Every path in a page is relative.** The site is published at `https://yanfengliu.github.io/textbook/`, a subpath, so one leading slash breaks it in a way that nothing at the root can see. `npm run subpath` is what catches it.
- **The handshake is the gates' only clock.** `window.__textbook.state` becomes `ready` when the shell has mounted, **every `<tb-sitting>` on the page has booted**, and, under `?eager=1`, every `<tb-figure>` on the page has registered and reached `ready` or `error`. The sitting term is **not** behind `?eager=1`, because `npm run devices` does not pass it and loads Today; on a page with no `<tb-sitting>` it is vacuously true and nothing is built, so every other page becomes ready at the instant it did before. A sitting has booted when its `.tb-standing` section holds anything, which is where both of `TbSitting.boot()`'s exits lead — `paintStanding()` on the good path and `fail()`'s `.tb-unavailable` panel on the bad one — so a sitting that has honestly given up releases the handshake instead of hanging it, and only a boot that neither paints nor fails holds the page in `loading` until the caller's own timeout. `window.__textbook.describeSittings()` reports what the handshake waited for.
- **The study system's three layers stay separate** (`docs/design/adaptive.md`): evidence is recorded in the browser, the scheduler is a pure function of that history and never calls a model, and the agent's round never schedules. A model re-deriving intervals is slower and worse than the arithmetic, and it cannot run while the reader is mid-sitting.
- **Mastery is tracked per objective, never per chapter or per question**, and every question names the objective it tests. An objective whose prerequisites are weak is blocked, not failed, and the queue works on the prerequisite.
- **No word the book shows about a reader may claim more than the record supports.** "Learned well" is the store's verdict — high recall, about a week of stability, a recent success, and success in two formats — and not the scheduler's `review` state, which only means a card is past its learning steps. `npm run sitting` holds this.
- **The prose is never hidden, locked, gated or reordered by the study system.** It annotates and it reorders practice. A reader may always read anything, including the parts they are bad at.
- **The reader's record is theirs and stays local.** `progress/` is git-ignored, nothing leaves the machine, and there are no accounts. What a round commits is its conclusions, not the raw log.
- Locally high-risk, so it gets independent review: the figure contract, the handshake, the scheduler and the mastery thresholds, the content checker's rules, and any change to `AGENTS.md` or `docs/design/`.

## Conventions

- One HTML page per chapter under `<book>/chNN-<slug>/index.html`, with `glossary.js` (its terms), `objectives.js` (the claims a reader should be able to make, and their prerequisites) and `items.js` (the review bank) beside it. Sections are `<section id>` with an `<h2>`; the shell numbers them. Every term the chapter introduces is a `<tb-term>`; every figure is cited by number in the prose; every question names its objective. No reader sees a question's options in the order they are written — Today and the chapter checks draw the order (`src/components/choice-order.js`) — so an explanation names an option by what it says, never by its letter or its place ("the last option", 「前两个选项」), and `npm run check` fails one that does.
- A study round is `.claude/commands/study-round.md`, run on evidence rather than on a timer, and it leaves a dated note in `docs/study/rounds/`. Nothing in this repo runs unattended.
- British spelling in the prose (organised, colour, metre); SI units with a space (20 µm); old-style figures in text, lining and tabular in tables.
- Figure modules live in `src/figures/<kind>.js`, registered in `src/figures/registry.js`; shared helpers in `src/figures/lib/`. Controls inside a stage use the `.fig-*` classes in `components.css`; figure-private styles are scoped under a unique class inside the figure's root.
- Devlog per canon: `docs/devlog/summary.md`, newest first, with detail in `docs/devlog/detailed/`. Work rounds in `docs/work/<id>_<theme>/`; worker handoffs and reviews in that folder's `reviews/`.
- `README.md` stays reader-facing: what the book is and how to open it. `docs/design/textbook.md` holds the design; `AGENTS.md` holds what builds and proves it.
- **The three standing records are looked up, not read.** `docs/learning/gate-proofs.md`, `docs/learning/defect-register.md` and a round's `docs/work/<id>_<theme>/plan.md` are append-only by design, each already runs to tens or hundreds of kilobytes, and each opens with a statement of the file's shape and an index of every entry, one line each. Read the top, then the entry the index names. Writing a new entry means copying the shape from that header — not reading a neighbour for the form. The live state of a round is the top section of its `plan.md`; everything under it is that round's narrative and is history, not instructions.
